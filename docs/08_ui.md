# Web UI Layer

## Overview

The RoboChess web UI is a single-page application served by a Flask backend. It provides a browser-based chess board that communicates with the game engine and arm controller over a REST API. The UI stack is designed around a critical constraint: **MuJoCo is not thread-safe** — the physics simulation must only be touched from the main Python thread, while Flask runs requests on separate worker threads.

The solution is a queue-based serialisation bridge (`QueuedUIBackend`) that receives HTTP requests on Flask threads, enqueues them, and drives them from the main thread via a polling loop.

---

## Architecture

```
Browser
  ↕ HTTP (JSON REST)
Flask server thread (daemon)
  ↕ queue.Queue[UIRequest]
Main thread (process_one loop)
  ↕ direct method calls
GameOrchestrator → PhysicalPlanExecutor → MuJoCo env
```

The main thread runs `backend.process_one(env=env, timeout=0.05)` in a tight loop, dequeuing requests and dispatching them to the orchestrator. Each Flask route blocks on a `queue.Queue` waiting for the main thread to finish processing its request.

---

## `UIBackend` Protocol (`src/ui/app.py`)

```python
class UIBackend(Protocol):
    def snapshot(self): ...
    def new_game(self): ...
    def submit_human_move(self, src: str, dst: str, promotion: str | None = None): ...
    def let_computer_play_current_turn(self): ...
```

`UIBackend` is a structural protocol (PEP 544). Any object implementing these four methods can be passed to `create_app()`. In production, this is `QueuedUIBackend`. In tests, `GameOrchestrator` is passed directly (it also satisfies the protocol, and tests don't need thread safety).

---

## `create_app(backend: UIBackend) → Flask` (`src/ui/app.py`)

Application factory. Creates a Flask app and registers all routes bound to the given backend. There is no global state — each call creates a fresh application.

### `to_jsonable(value)`

A recursive converter that turns dataclass instances (and nested structures containing them) into plain Python dicts/lists safe for `jsonify`. Works via `dataclasses.asdict` for dataclass leaves, with recursive descent for dicts and lists. This handles `GameSnapshot`, `MoveExecutionResult`, and their nested `GameStatus`.

## REST API Endpoints

### `GET /`

Serves the single-page HTML application (`src/ui/templates/index.html`). All UI logic runs in the browser from this page.

---

### `GET /api/snapshot`

Returns the current `GameSnapshot` as JSON. Used for polling the game state, and called automatically on page load.

**Response body** (`GameSnapshot` fields):

| Field | Type | Description |
|---|---|---|
| `fen` | string | Current FEN string |
| `turn` | string | `"white"` or `"black"` |
| `board` | object | `{square: piece_symbol \| null}` for all 64 squares |
| `physical_piece_ids` | object | `{square: piece_id \| null}` |
| `legal_moves` | array | UCI strings for all currently legal moves |
| `status` | object | `GameStatus` fields (is_check, is_checkmate, etc.) |
| `last_move` | string\|null | UCI of the most recent move |
| `move_history_san` | array | SAN notation history list |
| `is_busy` | bool | True while arm is moving |
| `error` | string\|null | Last error message, if any |

**Status code**: Always `200`.

---

### `POST /api/new-game`

Resets the chess logic and physical board state.

In production (via `QueuedUIBackend`), `process_one` intercepts `new_game` and calls `env.reset()` plus `physical_executor.reset_board_state()` before delegating to the orchestrator. This teleports all pieces back to their starting squares and resets MuJoCo physics.

**Response**: `GameSnapshot` of the new game starting position.
**Status code**: `200`.

---

### `POST /api/move`

Submits a human move.

**Request body**:
```json
{"src": "e2", "dst": "e4", "promotion": null}
```

`src` and `dst` are required. `promotion` is `null` for non-promoting moves, or `"q"`, `"r"`, `"b"`, `"n"` for promotion pieces.

**Validation**: Returns `400` with `{"accepted": false, "error": "src and dst are required"}` if either field is missing.

**Response**: `MoveExecutionResult` as JSON.

| Field | Description |
|---|---|
| `accepted` | Whether the move was legally valid |
| `physical_success` | Whether the arm executed it without error |
| `move_uci` | UCI string of the executed move |
| `error` | Error message if not accepted or physical failure |
| `snapshot` | Updated `GameSnapshot` |
| `awaiting_promotion` | Whether the move requires promotion choice (not yet used) |

**Status codes**: `200` if `accepted`, `400` if not.

---

### `POST /api/promote`

Placeholder for pawn promotion continuation. Currently returns `501 Not Implemented`. The promotion flow is currently handled by passing a promotion piece character directly in `/api/move`.

---

### `POST /api/let-computer-play`

Triggers the Stockfish engine to play the current turn.

**Response**: `MoveExecutionResult` as JSON.
**Status codes**: `200` if accepted, `400` if not (e.g., game over, wrong turn, engine not configured).

---

### `POST /api/undo`

Placeholder for move undo. Currently returns `501 Not Implemented`.

## `QueuedUIBackend` (`src/ui/queued_backend.py`)

### Responsibility

Bridges Flask worker threads and the main simulation thread. All state-mutating orchestrator calls are serialised through a `queue.Queue`. `snapshot()` is the only call that does not go through the queue — it returns a cached snapshot under a lock.

### Constructor

```python
QueuedUIBackend(orchestrator: GameOrchestrator)
```

- `_orchestrator`: the `GameOrchestrator` instance
- `_requests`: `queue.Queue[UIRequest]` — the serialisation queue
- `_snapshot`: latest `GameSnapshot`, initialised at construction
- `_lock`: `threading.Lock` protecting `_snapshot`

### `snapshot() → GameSnapshot`

Returns the cached snapshot under `_lock`. Does not enqueue a request. The cached snapshot is always at most one operation stale, updated atomically by `process_one` after each successful orchestrator call.

### `new_game()`, `submit_human_move(...)`, `let_computer_play_current_turn()`

All delegate to `_call(name, *args)`, which:
1. Creates a `UIRequest` with a fresh `queue.Queue(maxsize=1)` as its response channel
2. Puts the request in `_requests`
3. Blocks on `response.get()` until the main thread processes it
4. Returns the result or re-raises any exception

This means Flask handler threads **block** until the main thread finishes the move (including physical arm execution). Browser-visible "busy" state is conveyed by the `is_busy` field in `GameSnapshot`, which the JavaScript polls for.

### `process_one(env=None, timeout=0.05)`

Called by the main thread in a loop. Dequeues one `UIRequest` (blocking up to `timeout` seconds):

```python
request = self._requests.get(timeout=timeout)
```

If the request is `new_game` and `env` is provided, it first:
1. Calls `env.reset()` — resets MuJoCo physics
2. Calls `physical_executor.reset_board_state()` — teleports pieces to starting squares

Then dispatches to `orchestrator.{request.name}(*args, **kwargs)`, updates `_snapshot`, and puts the result in `request.response`.

Exceptions are caught and passed to the Flask thread via `response.put((False, exc))`, where `_call` re-raises them.

### `UIRequest`

```python
@dataclass
class UIRequest:
    name:     str          # orchestrator method name
    args:     tuple        # positional arguments
    kwargs:   dict         # keyword arguments
    response: queue.Queue  # single-slot response channel
```

## Main Thread Loop (`src/cli/play.py`)

```python
server = threading.Thread(
    target=lambda: app.run(host=..., port=..., debug=False, use_reloader=False),
    daemon=True
)
server.start()

try:
    while True:
        backend.process_one(env=env, timeout=0.05)
        if args.visualize:
            env.render()
        time.sleep(0.01)
except KeyboardInterrupt:
    pass
finally:
    env.close()
```

The Flask server runs as a daemon thread. The main thread loops calling `process_one` (which drains one request per call), optionally renders the MuJoCo viewer, and sleeps 10ms. This means:
- Latency from HTTP request to processing start: 0–60ms (next `process_one` invocation)
- During a full pick-and-place move, the main thread is blocked in `orchestrator.submit_human_move` for the duration of arm execution (potentially 10–30 seconds); the Flask thread blocks waiting for `response.get()`

### `build_controller(env, ...)` — Controller Factory

Builds the model-hybrid controller:

```python
controller = ModelEmbeddedController(env=env, render_fn=..., render_delay=...)
controller.load_all(
    transit_path=transit_model or model_paths.get("transit"),
    descend_path=descend_model or model_paths.get("descend"),
    ascend_path=ascend_model or model_paths.get("ascend"),
)
return controller
```

Model paths come from `configs/deployed_models.yaml` by default but can be overridden with CLI arguments.

### `build_orchestrator(env, ...)` — Orchestrator Factory

Wires together all components:

```python
registry = PieceRegistry()
occupancy = PhysicalOccupancy(registry.starting_square_map())
board_mapper = BoardMapper.from_configs()
controller = build_controller(...)
movement_executor = MovementExecutor(env, controller, board_mapper, occupancy)
physical_executor = PhysicalPlanExecutor(movement_executor, PieceTeleporter(env, board_mapper), occupancy, controller=controller, env=env)
engine_cfg = load_config("chess").get("engine")
chess_service = ChessService(engine_cfg=engine_cfg)
return GameOrchestrator(chess_service, physical_executor, LogicalPieceTracker(), engine_cfg=engine_cfg)
```

### `main()` — CLI Entry Point

Installed as `robo-chess-play`. Accepts:

| Flag | Default | Description |
|---|---|---|
| `--host` | `127.0.0.1` | Flask bind address |
| `--port` | `8000` | Flask bind port |
| `--no-visualize` | (visualize on) | Disable the MuJoCo viewer (headless mode) |
| `--delay` | `0.0` | Per-step render delay (seconds) |
| `--transit-model` | None | Override transit model path |
| `--descend-model` | None | Override descend model path |
| `--ascend-model` | None | Override ascend model path |

Startup sequence:
1. `regenerate_environment()` — validate/regenerate XML fragments
2. `gym.make("ChessFetchTask-v0", ...)` — create MuJoCo env
3. `env.reset()` — initialise physics
4. `build_orchestrator(...)` — wire all components
5. `QueuedUIBackend(orchestrator)` — wrap for thread safety
6. `create_app(backend)` — create Flask app
7. Start Flask daemon thread
8. Enter main processing loop

## Frontend (`src/ui/templates/index.html`, `src/ui/static/app.js`)

### HTML Structure

The page is a two-column layout:

```
.shell
├── .play-area
│   ├── .topbar (h1 title, subline status, Refresh/Flip buttons)
│   └── .board-frame
│       ├── #board (8×8 grid of button.square elements)
│       └── .files (a–h file labels)
└── .panel (aside)
    ├── .status-panel (turn display, state pill, last-move/legal-moves facts)
    ├── .actions (New Game, Let computer play buttons)
    ├── .history-card (SAN move history chips)
    ├── .fen-card (current FEN string)
    └── .error (error message display, aria-live)

#promotion-dialog (modal dialog for pawn promotion)
```

All interactive elements have `id` attributes for JavaScript binding. The promotion dialog is a native `<dialog>` element with four piece buttons (`data-piece="q"/"r"/"b"/"n"`).

### JavaScript State

```javascript
let snapshot = null;           // Latest GameSnapshot from server
let selected = null;           // Currently selected square (string or null)
let legalTargets = new Set();  // Legal destination squares for selected piece
let flipped = false;           // Board orientation (false = white at bottom)
let requestInFlight = false;   // True while a POST is pending
let pendingPromotion = null;   // {src, dst} while promotion dialog is open
let busyPollDelay = 200;       // Current busy-poll interval (ms)
let busyPollTimer = null;      // Timer handle for busy polling
```

### Board Rendering (`renderBoard()`)

Clears and rebuilds the 64-square board DOM from scratch on each state change. Each square is a `<button>` with:
- CSS classes: `square`, `dark`/`light`, optionally `selected`, `legal`, `last`
- `disabled` when `is_busy`, `requestInFlight`, or game over
- A `<span class="piece">` child if occupied (Unicode chess symbol)
- A `<span class="coord">` child showing the square name

Board orientation is controlled by `flipped`: when true, files are reversed (h→a) and ranks are reversed (1→8), showing the board from Black's perspective.

### Click Handling (`onSquare(square)`)

Two-click selection model:

1. **No piece selected**: clicking an occupied square selects it and highlights legal destinations.
2. **Piece selected, click same square**: deselect.
3. **Piece selected, click own piece (not in legal targets)**: re-select the clicked piece.
4. **Piece selected, click non-legal square**: deselect.
5. **Piece selected, click legal target**: attempt move.
   - If pawn promoting: open promotion dialog, store `pendingPromotion = {src, dst}`.
   - Otherwise: call `submitMove(src, dst, null)`.

The promotion dialog buttons dispatch to `submitMove(src, dst, piece)` with the chosen piece character. Cancelling the dialog clears `pendingPromotion` and deselects.

### API Communication (`postJson`, `loadSnapshot`)

`postJson(url, payload)`:
- Sets `requestInFlight = true`, re-renders (disabling all buttons)
- Sends POST with JSON body
- On success: updates `snapshot` from response (either `data.snapshot` or `data` directly)
- On HTTP or network error: calls `showError(msg)`
- In `finally`: clears `requestInFlight`, re-renders

`loadSnapshot()`:
- Sends GET to `/api/snapshot`
- Updates `snapshot` from the response

### Busy Polling (`scheduleBusyPoll`)

When `snapshot.is_busy` is true (arm executing a move), the UI schedules repeated `loadSnapshot` calls with exponential backoff:

```javascript
busyPollDelay = Math.min(1500, Math.round(busyPollDelay * 1.5))
```

Initial delay: 200ms. Maximum delay: 1500ms. Resets to 200ms when the arm finishes. This balances UI responsiveness against server load during long arm movements.

Note: This busy-polling is only needed when the server cannot push updates (no WebSocket). While the Flask thread blocks on `response.get()`, the browser has already received a `200 OK` from a prior snapshot or move response, and polls to detect completion.

### State Display

`stateKey()` maps current snapshot state to a CSS data attribute on the state pill:

| State | Condition |
|---|---|
| `busy` | `is_busy` or `requestInFlight` |
| `white-wins` / `black-wins` | Checkmate or `outcome` field |
| `draw` | `outcome == "1/2-1/2"` |
| `check` | `status.is_check` |
| `ready` | Otherwise |

`terminalReason()` produces human-readable draw/checkmate descriptions. `resultLabel()` produces the outcome string ("White wins", "Draw", etc.).

## Thread Safety Summary

| Component | Thread | Notes |
|---|---|---|
| `Flask` routes | Flask worker threads | Never touch MuJoCo state |
| `QueuedUIBackend.snapshot()` | Any thread | Lock-protected read of cached snapshot |
| `QueuedUIBackend._call()` | Flask worker threads | Blocks on response queue |
| `QueuedUIBackend.process_one()` | Main thread only | Only safe caller of MuJoCo and orchestrator |
| `GameOrchestrator` | Main thread only | No internal locking |
| `ChessSimulationEnv` (MuJoCo) | Main thread only | Not thread-safe |
