# UI Review — Flask API & Web Frontend

## Overview

The user interface consists of a Flask backend (`src/ui/app.py`) served via `scripts/run_chess_ui.py`, a Jinja2 HTML template (`src/ui/templates/index.html`), and a vanilla-JS single-page application (`src/ui/static/app.js`). Communication is synchronous JSON over HTTP; the frontend polls when the backend reports `is_busy`.

### Issue 1 — Promotion endpoint is unreachable dead code

```python
# app.py
@app.route("/api/promote", methods=["POST"])
def promote():
    return jsonify({"error": "not implemented"}), 501
```

Pawn promotion is a legal chess outcome. When a pawn reaches the back rank, `python-chess` marks it as requiring a promotion move (e.g. `e7e8q`). The `/api/move` endpoint will accept `e7e8q` as a UCI string if the frontend sends it, but:
1. The frontend has no promotion dialog — it cannot send a promotion suffix.
2. Without the suffix, `e7e8` is an illegal move and the endpoint returns 400.

Result: promotion is permanently broken. A pawn reaching the 8th rank freezes the game.

**Fix:** In `app.js`, after a move lands on rank 8 (or rank 1 for Black), show a piece-selection dialog (Q/R/B/N) and append the suffix to the UCI string before posting. On the backend, the existing `/api/move` path already handles the UCI string end-to-end — no server change needed.

### Issue 2 — `is_busy` blocks snapshot but not new-game

```python
@app.route("/api/snapshot")
def snapshot():
    return jsonify(orchestrator.snapshot())   # snapshot() includes is_busy

@app.route("/api/new-game", methods=["POST"])
def new_game():
    result = orchestrator.new_game()          # no busy-check
    ...
```

If the user clicks "New Game" while the arm is mid-move, `new_game()` resets the chess board immediately but the physical executor is still running. The arm will attempt to complete its move against a board that has been reset, then `return_to_home()` is called from the old thread. This creates a race between the reset logical state and the in-flight physical command.

**Fix:** Add a busy guard in `GameOrchestrator.new_game()` (mirror the pattern used in `_submit_move`) or return 409 from the route if `orchestrator.is_busy`.

---

### Issue 3 — No CORS headers / no authentication

All endpoints accept requests from any origin. For a local deployment this is harmless, but the app binds to `0.0.0.0` (from `run_chess_ui.py`), making it reachable on the local network with no access control.

**Fix:** Bind to `127.0.0.1` in development, or add `Flask-Login` / token auth if network exposure is intended.

---

### Issue 4 — `QueuedUIBackend` threading is sound but undocumented

`run_chess_ui.py:QueuedUIBackend` serializes all game requests through a `queue.Queue` processed by a dedicated worker thread. This prevents simultaneous physics calls. The implementation is correct; however, the interaction with `orchestrator.is_busy` creates a subtle state: `is_busy` is set/cleared inside `GameOrchestrator._submit_move`, which runs in the worker thread, while Flask reads `is_busy` from the main thread. Because CPython's GIL makes boolean assignment atomic, this is safe in practice, but a `threading.Event` would make the intent explicit and be correct across implementations.

## HTML Template (`src/ui/templates/index.html`)

The template is 70 lines of clean, minimal HTML. It exposes the required element IDs checked by `test_index_renders_interactive_controls`.

### Issue 5 — No board rank/file labels

The board SVG/grid has no rank (1–8) or file (a–h) labels. Players must mentally map coordinates. This is a usability gap, especially during debugging.

### Issue 6 — FEN display is raw, not formatted

The FEN string is rendered as plain text in a `<span>`. For developers this is useful; for end users it is confusing. A toggle (show/hide FEN) would be cleaner.

### Issue 7 — No promotion UI exists anywhere in the template

Consistent with the backend issue above: there is no modal, no piece-selection overlay, no inline selector. The template would need a `<dialog>` or hidden div added alongside a JS handler.

## JavaScript Frontend (`src/ui/static/app.js`)

### Issue 8 — `postJson` does not handle HTTP-level errors

```javascript
async function postJson(url, body) {
    try {
        const resp = await fetch(url, { method: "POST", ... });
        return await resp.json();
    } finally {
        setBusy(false);
    }
}
```

If the server returns a 4xx or 5xx, `resp.json()` still succeeds (the error body is valid JSON), but the calling code receives the error object without checking `resp.ok`. A 500 from the server will silently appear as a normal response with no visible error to the user.

**Fix:**
```javascript
const resp = await fetch(url, { method: "POST", ... });
if (!resp.ok) throw new Error(`HTTP ${resp.status}`);
return await resp.json();
```

---

### Issue 9 — Network failure silently clears busy state

If `fetch` throws (network down, server crash), the `finally` block calls `setBusy(false)` but no error is displayed. The board appears idle with no indication that the last move failed.

**Fix:** Add a `.catch(err => showError(err.message))` after each `postJson` call, reusing the existing `showError` function already defined in `app.js`.

---

### Issue 10 — Polling interval is fixed at 500 ms with no backoff

```javascript
if (data.is_busy) setTimeout(pollWhileBusy, 500);
```

A single physical move takes ~1.5s wall time (observed in debug log). The frontend will fire 3 redundant polls per move. For a long castling sequence this could be 6–10 polls. A 200 ms initial poll with 1.5× exponential backoff (cap 2000 ms) would cut server load without increasing perceived latency.

---

### Issue 11 — Selected-square highlight not cleared on illegal move

When the player clicks a source square, it is visually highlighted. If they then click an illegal destination, the backend returns 400. The current error path calls `showError()` but does not call `clearSelection()`, leaving the source square highlighted with stale state.

**Fix:** Call `clearSelection()` at the top of the `catch` / error branch of the move handler.

---

### Issue 12 — No visual indicator for check or game-over state

The snapshot payload includes `is_check`, `is_checkmate`, `is_stalemate`, and `result` fields (from `ChessService`). These are never surfaced in the UI. A player could be in checkmate with no visual cue beyond the legal-moves count dropping to zero.

**Fix:** Read `data.is_check`, `data.is_checkmate`, etc. from the snapshot response and update a status banner already present in the template (`<span id="state">`).

---

## CSS Quality

The stylesheet (inline in `index.html` / linked) renders a functional board. No accessibility attributes (`aria-label`, `role="grid"`) are present on the board element. Tab/keyboard navigation is unsupported.
