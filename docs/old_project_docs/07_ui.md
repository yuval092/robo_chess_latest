# User Interface

This document covers the web-based user interface: the Flask backend, the `UIBackend` protocol, the `QueuedUIBackend` wrapper, and the JavaScript frontend.

---

## 1. Architecture Overview

```
Browser (HTML/CSS/JS)
    │  HTTP (REST + polling)
    ▼
Flask App (src/ui/app.py)
    │  UIBackend protocol
    ▼
QueuedUIBackend / GameOrchestrator
    │
    ▼
GameOrchestrator  (chess logic + physical execution)
```

The UI is a **single-page application** served by Flask. The browser polls for state updates and submits moves via JSON REST endpoints. There is no WebSocket; the browser uses exponential-backoff busy-polling when the arm is moving.

## 2. Flask Application (`src/ui/app.py`)

### UIBackend Protocol

`UIBackend` is a Python `Protocol` (structural subtyping). Any class that implements these methods can be used as a backend:

```python
class UIBackend(Protocol):
    def snapshot(self): ...
    def new_game(self): ...
    def submit_human_move(self, src: str, dst: str, promotion: str | None = None): ...
    def let_computer_play_current_turn(self): ...
```

`GameOrchestrator` satisfies this protocol directly. In the threaded server, `QueuedUIBackend` (in `src/ui/queued_backend.py`) wraps `GameOrchestrator` and serializes all calls through a thread-safe queue.

### create_app(backend)

`create_app(backend: UIBackend) → Flask` builds and returns the Flask app. Routes:

| Route | Method | Description |
|---|---|---|
| `/` | GET | Renders `index.html` template |
| `/api/snapshot` | GET | Returns current `GameSnapshot` as JSON |
| `/api/new-game` | POST | Resets game; returns new snapshot |
| `/api/move` | POST | Submits a human move; returns `MoveExecutionResult` |
| `/api/let-computer-play` | POST | Triggers one computer move; returns result |
| `/api/promote` | POST | Not implemented (501) — promotion is handled inline via `/api/move` |
| `/api/undo` | POST | Not implemented (501) |

### /api/move payload

```json
{
  "src": "e2",
  "dst": "e4",
  "promotion": null
}
```

`promotion` is one of `"q"`, `"r"`, `"b"`, `"n"` or `null`. Returns 200 if accepted, 400 if rejected.

### to_jsonable()

All dataclasses (like `GameSnapshot`, `MoveExecutionResult`, `GameStatus`) are recursively converted to plain dicts/lists via `dataclasses.asdict()` before serialization. This handles nested dataclasses automatically.

### Response shape (`/api/move`, `/api/let-computer-play`)

```json
{
  "accepted": true,
  "physical_success": true,
  "move_uci": "e2e4",
  "error": null,
  "snapshot": { ... },
  "awaiting_promotion": false,
  "promotion_square": null
}
```

### Response shape (`/api/snapshot`, `/api/new-game`)

Direct `GameSnapshot` JSON:

```json
{
  "fen": "rnbqkbnr/pppppppp/...",
  "turn": "white",
  "board": { "e1": "K", "e2": "P", ..., "a8": "r", ... },
  "physical_piece_ids": { "e1": "white_king", ... },
  "legal_moves": ["e2e4", "d2d4", ...],
  "status": { "turn": "white", "is_check": false, ... },
  "last_move": null,
  "move_history_san": [],
  "is_busy": false,
  "error": null
}
```

## 3. HTML Template (`src/ui/templates/index.html`)

The template is a static HTML file rendered by Flask. JavaScript is loaded at the bottom (`app.js`). Styles are in `styles.css`.

### Layout structure

```
<main class="shell">
  <section class="play-area">
    <header class="topbar">        ← Title, subline, Refresh/Flip buttons
    <div class="board-frame">
      <div id="board">             ← 64 buttons, populated by JS
      <div id="files">             ← a–h file labels, populated by JS
  <aside class="panel">
    <section class="status-panel"> ← Turn, state pill, last move, legal count
    <section class="actions">      ← New game, Let computer play buttons
    <section class="history-card"> ← Move history chips
    <section class="fen-card">     ← Current FEN string
    <div id="error">               ← Error messages (aria-live)

<dialog id="promotion-dialog">    ← Promotion piece picker (HTML <dialog>)
```

### Promotion dialog

```html
<dialog id="promotion-dialog" aria-labelledby="promotion-title">
  <h2 id="promotion-title">Promote pawn to…</h2>
  <div class="promotion-choices">
    <button data-piece="q" aria-label="Queen">♛ Queen</button>
    <button data-piece="r" aria-label="Rook">♜ Rook</button>
    <button data-piece="b" aria-label="Bishop">♝ Bishop</button>
    <button data-piece="n" aria-label="Knight">♞ Knight</button>
  </div>
</dialog>
```

The `<dialog>` element is opened with `.showModal()` (modal) and closed with `.close()`. The `cancel` event fires if the user presses Escape.

## 4. JavaScript Frontend (`src/ui/static/app.js`)

The frontend is a ~300-line vanilla JavaScript file. No frameworks, no bundler.

### State variables

| Variable | Type | Description |
|---|---|---|
| `snapshot` | object | Most recent server snapshot |
| `selected` | string\|null | Currently selected square |
| `legalTargets` | Set | Legal destination squares for selected piece |
| `flipped` | bool | Whether the board is flipped (black's perspective) |
| `requestInFlight` | bool | True while a fetch is in progress |
| `pendingPromotion` | {src, dst}\|null | Promotion move waiting for piece selection |
| `busyPollDelay` | number | Current polling delay in ms (200–1500) |
| `busyPollTimer` | number\|null | setTimeout handle for busy poll |

### Board rendering (`renderBoard`)

1. Clears `#board` and `#files`.
2. Rebuilds 8×8 grid using `boardSquares()` (respects `flipped`).
3. For each square: creates a `<button>` with classes `square`, `dark`/`light`, plus conditional `selected`, `legal`, `last`.
4. Disables all board buttons when `is_busy`, `requestInFlight`, or `status.is_game_over`.
5. Appends piece Unicode character as a `<span class="piece white-piece|black-piece">`.
6. Appends square label as `<span class="coord">` (small, corner-positioned).

### Board orientation

- Normal (white's perspective): ranks 8→1 top to bottom; files a→h left to right.
- Flipped (black's perspective): ranks 1→8 top to bottom; files h→a left to right.

Dark/light squares: `(file + rank) % 2 === 0 ? "dark" : "light"`.

### Click handling (`onSquare`)

State machine with these transitions:

```
[nothing selected]
  click on own piece → select it, compute legalTargets, render
  click on empty/enemy → no-op

[piece selected]
  click same square → deselect
  click enemy with no legal target → re-select enemy if it has moves
  click enemy with no legal target + not own piece → deselect
  click legal target → submit move (or open promotion dialog)
  click non-legal empty → deselect
```

Terminal positions (`status.is_game_over`) are treated as no-op clicks. The state pill shows the result (`White wins`, `Black wins`, or `Draw`) and the subline includes the reason (`Checkmate`, `Stalemate`, insufficient material, repetition, or move-rule draw). The `Let computer play` button is disabled once the game is over.

### Promotion flow

1. `isPromotion(src, dst)` checks: is the piece a pawn (`"P"` for white, `"p"` for black) moving to the back rank (rank `"8"` or `"1"`)?
2. If yes: sets `pendingPromotion = { src, dst }`, calls `promotionDialog.showModal()`.
3. User clicks a piece button: `promotionDialog` click handler reads `btn.dataset.piece`, clears `pendingPromotion`, closes dialog, calls `submitMove(src, dst, piece)`.
4. User presses Escape: `cancel` event handler clears `pendingPromotion`, deselects, re-renders.

### submitMove / postJson

`submitMove(src, dst, promotion)`:
- Calls `postJson("/api/move", {src, dst, promotion})`.
- On success: calls `loadSnapshot()` to refresh state.

`postJson(url, payload)`:
- Sets `requestInFlight = true`, triggers a render (disables buttons).
- Sends `POST` with `Content-Type: application/json`.
- Checks `response.ok` — non-2xx responses show `data.error` or `"Server error {status}"`.
- Network errors are caught and shown via `showError()`.
- Always clears `requestInFlight` in `finally`, triggers re-render.
- Returns the parsed data on success, null on failure.

### Busy polling (`scheduleBusyPoll`)

When `snapshot.is_busy` is true (arm is moving), the frontend polls:

```javascript
function scheduleBusyPoll() {
  if (busyPollTimer !== null) return;  // no double-schedule
  busyPollTimer = setTimeout(async () => {
    busyPollTimer = null;
    if (!snapshot?.is_busy) { busyPollDelay = 200; return; }
    await loadSnapshot();
    busyPollDelay = Math.min(1500, Math.round(busyPollDelay * 1.5));
    if (snapshot?.is_busy) scheduleBusyPoll();
    else busyPollDelay = 200;
  }, busyPollDelay);
}
```

- Initial delay: 200ms.
- Backoff: × 1.5 each poll, capped at 1500ms.
- Resets to 200ms when arm becomes idle.
- `busyPollTimer !== null` guard prevents concurrent timers.

### renderSnapshot

Called after every state change. Updates:
- `#turn`: `"White"` or `"Black"`
- `#state` + `data-state` attribute: `"Ready"`, `"Busy"`, `"Check"`, `"Checkmate"`, `"Stalemate"`, `"Game over"`
- `#subline`: `"{state} · {color} to move"` or error message
- `#last-move`: last UCI move or `"-"`
- `#legal-count`: number of legal moves
- `#fen`: current FEN
- `#history`: move history chips (one per move, numbered)
- `#error`: error message
- Button disabled states
- Calls `renderBoard()`
- If `is_busy`, calls `scheduleBusyPoll()`

## 5. CSS (`src/ui/static/styles.css`)

Key visual elements:

- **Shell layout**: CSS Grid with `play-area` (board) and `panel` (sidebar) side-by-side.
- **Board**: 8×8 CSS Grid, square buttons with `light`/`dark` background colors.
- **Selected square**: highlighted border/background.
- **Legal target dots**: small indicator dots on legal destination squares.
- **Last move highlighting**: `last` class on source and destination of the previous move.
- **State pill**: color-coded `#state` element — green for Ready, yellow for Check, red for Checkmate, etc. (controlled via `data-state` attribute CSS selectors).
- **Move history chips**: flexbox row of `span.move-chip` elements.
- **Promotion dialog**: centered modal with backdrop. `.promotion-choices` is a flex row of large piece buttons.
- **Piece colors**: `.white-piece` (light-colored Unicode) vs `.black-piece` (dark-colored Unicode).

## 6. Server Entry Point (`src/ui/queued_backend.py`)

The actual server startup is in `src/ui/queued_backend.py`. It:

1. Builds the full simulation environment (MuJoCo + chess scene).
2. Constructs `GameOrchestrator`.
3. Wraps it in `QueuedUIBackend` — which serializes all API calls through a `queue.Queue` processed on the main thread (required because MuJoCo is not thread-safe).
4. Creates the Flask app with `create_app(backend)`.
5. Starts Flask in a background thread.
6. Runs the MuJoCo viewer in the main thread (interactive 3D visualization).
7. The main thread also drains the `QueuedUIBackend` request queue on each viewer step.

This architecture ensures:
- Flask can handle HTTP requests concurrently.
- All MuJoCo calls happen on the main thread.
- The viewer stays responsive while the arm is moving.

---

## 7. Headless Mode

The UI can also run without the MuJoCo viewer (e.g., for CI or testing). In this mode, the `GameOrchestrator` uses a mock or stub `physical_executor` that returns success without calling into MuJoCo.

## Queued Backend Location

`QueuedUIBackend` is implemented in `src/ui/queued_backend.py`. `scripts/run_chess_ui.py` is a thin wrapper around the packaged `src.cli.run_chess_ui` entry point.
